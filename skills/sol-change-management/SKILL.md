# Sol Change Management

## Core Rule

Use this skill for Sol controlled-document change packages. Start by reading `references/sol-ecr-workflow.md`; it contains the reusable workflow, Smartsheet conventions, and guardrails.

## Default Workflow

1. Locate the latest/proposed working controlled document and the prior released controlled baseline, using local synced SharePoint folders before web access.
2. Inspect only the released or working controlled documents when identifying changes and impacted docs. For every changed or impacted document being compared, audit the complete release-to-working delta across all worksheets, sections, tables, formulas, requirements, diagrams, captions, embedded graphics, freeze/visibility settings, and other review-relevant structures; do not stop after finding the expected CDL change.
3. Classify every material delta actually present between the released baseline and working revision as belonging to the active CDL, another known CDL, concurrent/unattributed content, or a release check. Show complete-document working-revision changes when needed for release review, but keep concurrent changes explicitly separated from the active CDL approval scope. Do not present content already released in the baseline as a current or concurrent change.
4. Create or update a package under the workspace `Change Management` folder.
5. Generate a change summary markdown file as the editable source artifact.
6. Generate or refresh the change summary PDF from the markdown using `scripts/render_change_summary_pdf.py`. Treat the generated PDF as the WAS/IS Change Artifact for Smartsheet attachment.
7. Include an `Impacted Docs Assessment` section in every change summary. Use the standard `Likely Impacted Released Docs` table pattern from `references/sol-ecr-workflow.md`.
8. Draft the Change and Decision Log row locally first, pointing the attachment fields at the generated PDF.
9. Ask Kyle for missing rationale, classification, assessors, impacts, or approval before writing to Smartsheet unless he has explicitly confirmed the write.
10. Before any official write, check the live sheet for an existing matching row.
11. When approved, create or update the Smartsheet row, attach the generated change summary PDF, then save local records of row ID, object ID, attachment ID, and API responses.

## Standing Conventions

- Interpret `Related Docs?` as the changed subject document plus impacted released Systems documents that the proposed change will drive updates into.
- List the changed subject document first, then downstream impacted docs. Do not include generated files, raw notes, local artifacts, or docs that merely consume/reference the source unless they require updates.
- Do not create numbered change items for unchanged areas. If a compared tab, section, figure, or document area did not change, omit it from the CR list; mention it only as concise review evidence when it materially helps reviewers.
- Format every numbered change-item heading exactly as `CR# - [DOC NAME], Change title`, where `#` is the sequence number without an added hyphen, `[DOC NAME]` is replaced by the controlled document name without literal brackets, and the title follows the comma. Example: `CR1 - Detection ICD, Correct C3x18 pin mapping`.
- Treat each released revision as an immutable comparison point. If someone edited a released copy in place, use the restored released file as the baseline and the newly created working revision as the proposed file. Do not include changes already present in that restored released baseline, do not show them as concurrent WAS/IS evidence, and do not narrate the mistaken released-copy edits unless Kyle explicitly requests an audit trail.
- When rerunning an assessment after source updates or corrections, rewrite the package to show the actual deltas between the last released baseline and the current proposed revision. Do not narrate previous agent inspections, temporary content that was removed, false starts, or earlier observations that are no longer true unless Kyle explicitly asks for an audit trail.
- Use a `Compared Source Artifacts` section, not a loose `Source Files` bullet list, in generated change summaries. Present only controlled documents that are the changed subject documents or likely impacted controlled documents being directly compared for a required update. Do not include CDL rows, changelogs, raw notes, generated package files, or other context/supporting sources in this table. Do not include downstream documents inspected only to determine that there is no impact; place those in the `Reviewed But Not Directly Impacted` impact-analysis table instead. Use columns `Role`, `Released/Baseline`, `Current/Proposed`, and `Evidence Used`, with privacy-safe SharePoint-relative labels for controlled artifacts.
- Scope impact evidence to released or working controlled documents only. Do not use supplemental information such as loose graphics folders, worksheets, exports, drafts, raw notes, CDR delivery folders, `Old` folders, extracted media folders, local generated artifacts, or side calculations as impact-assessment drivers unless Kyle explicitly asks for a separate supplemental review.
- For spreadsheet or database-like ICDs, compare every worksheet and distinguish raw coordinate churn from material logical-record changes. Normalize inserted/deleted-row formula references or stable record identities before concluding that many cells represent many design changes. Record table-range, added/removed row, formula, freeze-pane, hidden/visible column, validation, chart, and embedded-object changes when they affect release review.
- When a change is visual, graphical, layout-based, or figure-driven, generate change-summary graphics such as before/after crops, annotated context screenshots, or extracted figure comparisons. Store generated images under the package `assets/` folder and embed each visual directly inside its associated change item section so it appears in the generated PDF. Do not list the images as separate Smartsheet attachments unless Kyle explicitly requests separate image files.
- Before finalizing any visual, graphical, layout-based, or figure-driven controlled-document package, perform a whole-document embedded-figure audit against the released baseline and current/proposed document. Inventory every figure caption, embedded media target, media hash, image format, and image dimensions; then classify each figure as unchanged/renumbered, changed, added, or removed. Visually inspect every changed/added/removed figure candidate before deciding whether it belongs in the change summary. Do not rely only on known captions, expected figures, or the first few obvious changes.
- Label before/after images explicitly as `WAS` for the old/baseline picture and `IS` for the new/current picture. Prefer side-by-side equal-width WAS/IS image pairs in the PDF; if the figures do not fit cleanly side by side, stack them vertically but keep the WAS/IS labels next to the images.
- Annotate changed regions in figures and diagrams with a conspicuous box, arrow, or callout. When one figure contains changes from multiple CDLs, use scope-coded annotations and a clear legend or label so the active CDL evidence cannot be confused with concurrent changes. Include enough surrounding context to identify the changed interface.
- When a polished graphic already presents a table-level WAS/IS delta, do not repeat the same rows in an adjacent Markdown table. Use a short lead-in plus the graphic as the sole detailed presentation. Keep standard Markdown tables for `Compared Source Artifacts`, `Impacted Docs Assessment`, and other cases where the graphic does not encode the same information.
- After any markdown or graphics edit, regenerate the package PDF and make the Smartsheet draft/payload identify that PDF as the primary attachment. Keep the markdown as the editable source in the local package.
- Ensure generated WAS/IS PDFs include the Quantinuum template-style footer marking: plain footer text, no colored footer background, `Quantinuum Internal Only` centered, and generated date plus page count on the right.
- Keep impacted-docs assessment content in the standard markdown tables from `references/sol-ecr-workflow.md`; the renderer converts those tables into print-friendly field cards in the generated PDF and recovers common literal-pipe interface strings.
- Do not wait for an explicit request to inspect graphics when the source change is visual, figure-driven, layout-based, or likely duplicated in downstream figures. Treat controlled documents requiring graphics updates as impacted docs; treat generated comparison images as evidence attachments only.
- Use actual controlled-document evidence for graphics impact calls. Do not list a document as impacted based on supplemental graphics, exported art files, adjacent graphics folders, or other non-document source material.
- Leave Smartsheet auto/system fields blank on row creation, including `Row ID` and `Date Added`.
- Use `Disposition = New` and `Implemented? = No` for a new proposed row unless Kyle or ERB provides another lifecycle state.
- Treat implementation as a single row-level status: check/mark implemented only when all impacted docs are updated and released.
- Treat `Decision or Change Output` as the released-document completion log, not a proposed approval narrative. Leave it blank on new/proposed rows unless one or more impacted documents have actually been released. Once a document is listed in that field, treat that document as released/done for the change. Keep `Implemented? = No` or `In Process` until every impacted document listed in `Related Docs?` is released, then set `Implemented? = Yes`.
- For Sol Technical Baseline updates, read the existing baseline table first and treat it as the previous weekly snapshot before refreshing from local Systems files and the live CDL.
- For Sol Technical Baseline notes, keep the weekly table concise. Open CDL impacts should be listed as `SOL-###-CDL - <short keyword label>` using the CDL description/title as the source; do not include detailed change-package bullets. Continue omitting `Approved`, `Approved+DONE`, `Cancelled`, and `Rejected` rows after their redline window, and for `Approved+WIP` rows with multiple impacted docs, omit documents already named as released in `Decision or Change Output` after their redline window. Leave notes blank when there is no pending revision or open CDL impact.
- For Sol Technical Baseline weekly redlines, keep only the current refresh window redlined. At the start of each refresh, normalize prior-window blue revision values and blue open-impact notes back to plain text, and remove prior-window struck/released CDL notes that are now closed for that document. Then mark only changes from the current refresh in blue for one week. If a CDL impact released/closed for a document since the previous snapshot, keep the `SOL-###-CDL - <short keyword label>` note visible with strikethrough and blue font for the current one-week window, then remove it on the next refresh unless Kyle asks to keep older history. Add only the current redline window dates in the table header; do not extend or accumulate older windows.
- In user-facing final responses, Smartsheet drafts, and change summaries, avoid exposing full local absolute paths that include `C:\Users\<name>`. For controlled documents in the locally synced Sol SharePoint tree, use a known-good SharePoint web URL only when it was copied from SharePoint, Smartsheet, OneDrive metadata, or another authoritative source. Do not invent SharePoint URLs by string-converting a local sync path. If no known-good URL is available, present a SharePoint-relative label instead, such as `Sol Project Team Channel/Systems/ICDs/...`. For local-only generated package artifacts, use workspace-relative labels such as `Change Management/<package>/<file>` until the artifact is attached to Smartsheet or otherwise has a verified URL.
- Do not write raw Smartsheet tokens into files, logs, prompts, or final responses.

## Smartsheet Write Discipline

Live Smartsheet operations are production edits. Prepare review artifacts first. After Kyle confirms, create exactly one row, attach the generated WAS/IS PDF, and verify the row. If an attachment fails after row creation, retry attachment against the created row; do not create a duplicate row.
